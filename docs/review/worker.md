## 2. 严重度定义

| 级别 | 含义 |
|---|---|
| P0 | 数据丢失、安全漏洞，或常见的崩溃 |
| P1 | 功能错误，或较常见的可靠性问题（本报告把违反目标网站 robots.txt 的问题也归入 P1） |
| P2 | 边界情况，或对可维护性影响较大 |
| P3 | 代码风格、轻微问题 |

“验证”一栏写建议的测试类型：
- **单元**：xUnit + Moq（`HttpMessageHandler` 用模拟处理器）就够。
- **集成**：需要 `CrawlerCore.Tests/Integration/` 的进程内 Master + 真实 Worker。
- **人工**：只能人工复测（例如需要 Docker、真实网络环境或真实启动方式），T5 交付时要列出步骤。
- **真实请求**：需要对 arXiv 发少量真实请求（间隔不少于 15 秒，遵守 robots.txt）。

2. **两端协同**：
   - W-02 依赖 M-09（启用认证拦截器后保留 `PermissionDenied` 等状态码）和 M-03（重新注册不再被旧会话拒绝）。T4 若未完成 M-09，Worker 也要把 `Internal` 当作可重试错误，不能退出。

   - W-23 即 M-04 ④；W-27 是 M-11 的 Worker 侧；W-28 与 M-19 一起，建议放到 T6 设计。
3. **数据质量先于 T6/T7**：W-05、W-06 必须在 T6 之前修好，T6 的 API 插件要与修好后的 ThesisPlugin 输出一致（W-25 的契约测试同时覆盖两者）。**`D:\毕设相关\数据分析\元数据\` 里的现有数据中 99.8% 的论文只有第一作者，用它构建作者合作网络几乎没有边**；T7 应以 T6 重新采集的数据为主，原有数据只能用来验证流程能跑通。

5. **构建与部署一起改**：W-04、W-18 都改插件的打包与加载；W-11、W-13、W-24 都影响部署（退出码、配置、Docker），建议同一批修改，并同步 `docs/project/deployment.md`。

## 6. 写得好、应保持的设计

T5 修改时，以下设计应当保留：

1. **所有写入经过 `Channel<FromWorker>`（`SingleReader`），由单一写循环串行写流**（`SendMessageAsync` / `StartWriteLoopAsync`），心跳、进度、结果之间不会争用 `RequestStream`。W-03 把通道改为进程级时保留这一点。
2. **Master 消息在读循环中按到达顺序处理**，每个事件订阅者各自 try/catch，一个订阅者出错不影响流。
3. **并发任务用 `SemaphoreSlim` 限流，每个任务一个链接到全局令牌的 CTS**，为 T9 的暂停/取消和 W-01 的停止流程留好了接口。
4. **引擎的基本骨架是对的**：BFS 队列加规范化去重（去掉片段、统一主机大小写）；关闭自动重定向后手动跟随，有次数上限和循环检测；用异常过滤器 `when (!ct.IsCancellationRequested)` 区分超时与取消；使用 `IHttpClientFactory` 的命名客户端，而不是每次 `new HttpClient`。
5. **插件接口用默认接口方法扩展**（`ShouldFollowLink`），老插件不用改；ThesisPlugin 用白名单（只允许 `/abs/`）限定作用域，并自带 15 秒间隔。W-18、W-30 新增的接口方法沿用这种方式。
6. **parsedData 的值统一转成字符串，列表转成 JSON 数组**，与 proto 的 `map<string, string>` 和 DataAnalysis 的 `json.loads` 对得上（W-32 只调整标量的格式）。
7. **节点信息采集逐项降级**：每一项都有自己的 try/catch，失败时返回 0，不会中断心跳；读取 cgroup v2 的 CPU 配额和内存上限；NodeId 做了规范化（非法字符替换、长度限制）；用 UDP `Connect` 取得通往 Master 的出口 IP。
8. **注册按状态码区分可重试与不可重试**（`ExecuteRegistrationWithRetryAsync` 遇到 `Unauthenticated`、`AlreadyExists`、`InvalidArgument` 直接终止），并有总超时。W-02 把同样的思路用到流上。
9. **进度节流与终态强制上报**：运行中的进度按间隔上报，Completed/Failed 不受节流限制。
10. **`GrpcClientManager`**：线程安全的懒创建与重建通道、消息上限与 Master 对齐、Gzip 压缩、关闭时有超时。
11. **服务注册抽成 `AddCrawlerWorker`**，Program.cs 与集成测试共用一套（T1），测试开启了 `ValidateScopes`/`ValidateOnBuild`。
12. **T1 的测试基础设施**：`TcpFaultProxy` 区分“RST 崩溃”和“黑洞失联”两种故障；等待一律轮询加超时；`TestNodeInfoCollector` 只替换必须替换的部分；已知缺陷写成“修复后应有的行为”并 Skip，修好即成为回归测试。T5 修完 W-01、W-02 后直接去掉对应的 Skip。

### 7.3 配置与部署的变化

- Worker `appsettings.json` 的令牌改为空，`MasterEndpoint` 默认 `http://localhost:5001`（在本机运行 Worker 不用再改配置）；Docker 镜像通过 `MASTER_ENDPOINT` 默认连接 `http://host.docker.internal:5001`。令牌必须通过 `NODE_AUTH_TOKEN` 或 `GrpcSettings__NodeAuthToken` 提供，详见 `docs/project/deployment.md`。
- 新增配置项：`GrpcSettings` 的 `MaxRetryDelaySeconds`、`MasterResponseTimeoutSeconds`、`ResultAckTimeoutSeconds`（Worker 也使用 `KeepAlivePingDelaySeconds`/`KeepAlivePingTimeoutSeconds`）；`CrawlerSettings` 的 `RobotsCacheHours`、`MaxRequestRetries`、`MaxResponseBytes`、`SameHostOnly`、`PluginTimeoutSeconds`、`PluginDirectory`、`IgnoreCertificateErrors`。
- Worker 输出目录的插件布局改为 `Plugins/<插件名>/`；旧版本留在 `Plugins/` 下的单个 DLL 仍会加载，重名时以子目录中的为准（记 Error 日志）。
